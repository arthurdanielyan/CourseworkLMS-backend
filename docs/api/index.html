Library Management System · API v1

LMS API Reference

What the backend accepts and returns today: account access (signup with an email code, login, token refresh, logout, password reset, your own account), the book catalog (search with filters, book details, filter lists), Favourites, Reviews, Reservations, the Waitlist, and adding, editing and deleting books. Generated from the backend's code on every change to the endpoints. This page is read-only and cannot send requests.

Rules that apply to every endpoint

  • Every path starts with /api/v1, and every JSON field is snake_case: full_name, access_token.
  • Authenticated requests send Authorization: Bearer <access_token>. The /api/v1/auth/** endpoints need no token.
  • A signup only accepts @polytechnic.am emails. The server picks the role: teacher for emails on the teacher list, student for everyone else.
  • Passwords are 8–72 characters, with upper and lower case letters, at least 2 digits and at least 1 special character.
  • After login, GET /api/v1/me gives the user's name, email, role and permissions; use it to choose which screens to show rather than reading the access token. POST /api/v1/auth/logout with the refresh token ends that session and needs no access token. POST /api/v1/me/password logs out every other device and returns a new token pair for this one.
  • A forgotten password is reset in three calls under /api/v1/auth/password-resets: start (emails a code; an email without an account gets the same answer, but no email), /verify (checks the code without using it up) and /complete (sets the new password and logs out every device). The code follows the signup rules: 6 digits, 10 minutes, 5 tries, a new one every 2 minutes.
  • Lists are paged with ?page=0&size=20 (page counts from 0, size up to 100). The filter lists (categories, languages, owners) are short and come whole.
  • A filter that takes several values repeats the parameter: ?category_id=2&category_id=3. Values of one filter match if any of them matches; different filters must all match.
  • A book with no owner is a University Book: owner is null, and the search finds them with university=true.
  • Every book carries favourite for the logged-in user. PUT and DELETE /api/v1/favourites/{book_id} answer 204 even when nothing changes, so the heart button can send them without checking first.
  • Each user has at most one Review per book, at /api/v1/books/{book_id}/reviews/mine: PUT writes or replaces it, DELETE removes it. The Positive filter is stars=4&stars=5, the Critical one stars=1&stars=2.
  • A Reservation goes reserved → borrowed (an admin hands the copy over) → returned (an admin takes it back). A reserved one becomes cancelled when its user cancels it, or expired when nobody picks it up by pickup_deadline, 48 hours after reserving. The return date is chosen when reserving: after today and at most the book's max_loan_days from today, counted in Yerevan time.
  • An Unavailable book has a Waitlist. When a copy comes back, it is held for the first user in line for 24 hours: their entry in /api/v1/waitlist/mine gets offer_expires_at. They accept by reserving the book as usual, and decline by leaving the waitlist. Unanswered, the copy passes to the next in line, or back on the shelf when nobody is waiting.
  • Books are added and edited with authors and the publisher given by name: a name the library already has (ignoring case) is reused, a new one is added. /api/v1/authors?q= and /api/v1/publishers?q= autocomplete them. A teacher's book is their own and starts with no copies; an admin's is a University Book. Only admins send total_copies and max_loan_days.
  • A cover (JPEG, PNG or WebP, up to 5 MB) or PDF (up to 50 MB) is uploaded with PUT /api/v1/books/{id}/cover or /pdf as multipart/form-data with one part named file. The book's cover_image_url and pdf_url then point to /api/v1/files/{id}, which needs no token.

401 means only one thing: the access token is missing, expired or invalid. Call POST /api/v1/auth/refresh with the refresh token, store the new pair, and retry. Wrong passwords, bad codes and bad refresh tokens answer 400, so a refresh loop can't happen. Logged in but not allowed is 403.

Error format

Every failure is a problem response (RFC 9457). Switch on code; detail is for people. Validation failures also list the rejected fields, named as the client sends them.

{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "The request is invalid.",
  "code": "validation_failed",
  "errors": [
    { "field": "full_name", "message": "size must be between 2 and 100" }
  ]
}
